# 증거 시각화와 실제 렌더 제작 · v1.5.0

IR 제작 요청에는 장표별 증거 시각화와 제품 사진·화면 기획을 포함한다. 사용자가 다시 “이미지를 넣어 달라”고 말할 때까지 기다리지 않는다. 현재 자료와 주장에 맞춰 원본 활용, 공식 자료 조사, 설명용 생성, 편집 가능한 표·차트·도식을 선택한다. 원고·근거·이미지의 실제 상태와 도구 사용 범위를 지키며 필요한 제작을 진행한다.

이 절차는 [디자인과 피칭](design-and-pitch.md), [조사 절차](research-protocol.md), [계약](contracts.md)을 함께 따른다. 이미지 생성·편집에는 현재 제공된 관련 도구와 지침을 사용한다. 도구가 없거나 필요한 원본에 접근할 수 없으면 그 한계와 가능한 대안을 기록한다. 생성 도구의 실행 성공이 사실·권리·디자인 검수 완료는 아니다. 생성 자산의 source에는 사용한 도구, 작업 기록의 위치, 생성일을 남기고 rights의 판단에는 사용·공개 범위와 확인 근거를 기록한다. AI 생성이라는 이유만으로 owned를 자동 기입하지 않는다.

## 1. 주시각물과 근거를 장표마다 정한다

각 장표에서 먼저 보여 줄 증거를 고른다. 질문의 답과 논거를 보고 주시각물, 근거 상태, 가상 표기, 줄일 본문, 프레임과 읽는 순서, 보존할 보조 논거를 계획한다. 제목·본문을 먼저 채운 뒤 빈 곳에 그림을 붙이지 않는다.

`visual_brief`의 다섯 필드는 실제 `blocks`와 일치해야 한다. `primary_block_id`는 가장 먼저 읽을 증거를, `reading_order`는 모든 블록을 가리킨다. 출처·단위·중요 가정·비교 조건을 줄여 없애지 않는다. 계획 metadata를 저장했어도 제작기가 반영하지 않았다면 시각화가 구현된 것이 아니다.

새 프로젝트는 `require_visual_briefs: true`와 `require_visual_plan: true`를 유지한다. `design/visual-plan.json`은 `schema_version: "1.0"`과 `slides` 배열로 모든 사용 장표의 선택과 준비 상태를 기록하며 design 단계부터 검사한다. 각 장표 항목의 필드는 다음과 같다. 정확한 검증 규칙은 [계약](contracts.md)을 따른다.

| 필드 | 기록 내용 |
|---|---|
| `slide_id` | 현재 공통 장표 풀의 ID |
| `block_ids` | 실제 표시할 현재 장표의 블록 ID 배열. 필수 |
| `evidence_ids` | 시각물이 설명하는 현재 근거 ID |
| `visual_type` | `photo`/`product_ui`/`chart`/`table`/`diagram`/`quote`/`mixed` 중 실제 주시각물 |
| `source_strategy` | `original`, `official`, `generated`, `native` 중 주된 제작 경로 |
| `asset_refs` | 선택 객체 배열. 자산 없는 native 장표는 빈 배열. 아래 자산 필드와 실제 장표의 path를 연결 |
| `disclosure` | 장표에 표시할 가상·예시·가정·미확인 문구 |
| `claim_boundary` | 이 시각물이 뒷받침하는 주장과 뒷받침하지 않는 주장 |
| `status` | `planned`, `ready`, `missing` |
| `search_note` | 확인한 자료·검색 범위·선정/제외 이유·제약 또는 이미지 미사용 사유 |

`planned`/`missing` 파일은 자산 제작 전에도 저장할 수 있다. 초기 기획·원고 단계에는 visual-plan 완료 검사를 호출하지 않는다. design 완료·결과 게시 시점에는 실제 연결 자산과 ready 상태가 필요하므로 미완성 계획이 차단되는 것이 정상이다. 존재하지 않는 해시·사용권을 채워 통과시키지 않는다.

`ready`는 해당 시각물이 준비되어 실제 블록에 연결됐다는 뜻이다. 제품 구현이나 고객 반응이 검증됐다는 뜻이 아니다. `native`는 외부 이미지 없이 표·차트·도식으로 표현한다는 선택이며, 사용한 수치와 사실은 여전히 근거를 필요로 한다. 복합 장표의 나머지 자산도 각 블록과 자산 대장에서 추적한다.

`asset_refs`의 각 객체에는 `path`, `sha256`, `source`, `rights`, `origin`, `caption`, `claim_boundary`가 필요하다. `rights`는 확인한 `owned`/`licensed`/`permission`/`public-domain`, `origin`은 `original`/`official`/`generated` 중 하나다. path는 block_ids가 선택한 image 블록 또는 steps.items[].asset의 path와 연결하고 파일 존재·현재 SHA256·출처·권리를 확인한다. 생성 자산은 상위 `disclosure`와 자산 `caption`에서 생성·가상·설계·예시 상태를 명확히 표시한다. AI라는 단어만으로 생성 이미지임을 대신 표시하지 않는다.

design 단계의 ready 계획은 양 view에서 쓰는 모든 장표를 포함해야 한다. `evidence_ids`에는 현재 evidence의 ID를 연결한다. 사업 실증 근거가 없다면 설명하는 설계·가정의 근거를 assumption으로 정확히 연결하고, 실제 실적의 확인된 근거인 것처럼 바꾸지 않는다. 자산과 계획 필드의 존재만으로 직접 판독이나 권리 확인을 대신하지 않는다.

## 2. 주장에 맞는 표현과 자료 경로를 선택한다

| 내용 관계 | 표현과 자료 경로 | 보존할 경계 |
|---|---|---|
| 실제 제품·사용 현장 | 팀 원본 화면·사진을 먼저 판독하고 중요한 부분 확대 | 제품 버전·촬영 맥락·구현 상태 |
| 시장·기술·경쟁 근거 | 공식 통계·원문·공식 기능 자료와 관련 이미지 조사 | 기간·대상·단위·확인일·자사 적용 한계 |
| 제품 설계·생활 상황 | 확인한 기능 사양에서 설명용 제품 사진·화면·장면을 기획하고 필요시 생성 | 실제 구현·사용자·실험의 증거가 아님 |
| 비교·정량 데이터 | 편집 가능한 동일 조건 표·native chart | 원본 값·비교축·단위·출처 |
| 미확정 시장·운영·검증 | 범위·교집합·계산식·분모·진행 조건의 native 도식 | 가정·계획·미확정 상태, 도형 크기의 의미 |
| 팀·일정 | 확인된 경력과 책임, 목표·기간·담당·산출물·검증 기준 | 실제 인력과 확보 예정 인력, 달성 여부 |

연구자는 주장에 직접 연결된 원본·공식 근거 이미지와 재사용 조건을 조사한다. 공개된 이미지나 검색 미리보기를 허가된 최종 자산으로 취급하지 않는다. 권리를 확인하지 못하거나 적합한 이미지가 없으면 확인한 사실 데이터의 native chart, 표 또는 근거 관계 도식으로 전환한다. `search_note`에 실제 조사와 전환 이유를 남기며, 조사하지 않은 검색을 꾸며 쓰지 않는다. 이미지가 필요 없는 산식·일정·비교는 처음부터 `native`를 선택하고 이유를 기록할 수 있다.

제품 장표의 핵심 작동을 텍스트만으로 대체하지 않는다. 실제 화면이 없다면 확인한 설계 범위 안에서 가상 화면을 만들어 표시한다. 사용자가 기본 기능을 주고 직접 기획을 요청했다면 그 범위 안의 세부 UI·외형을 assumption으로 제안·제작할 수 있다. 핵심 기능 자체를 알 수 없을 때만 필요한 기능·화면을 `missing`으로 남긴다. 생성으로 근거 공백을 해결 처리하지 않는다.

## 3. 재사용할 핵심 자산을 준비한다

장표마다 별개 이미지를 생성하기보다 사업의 핵심 제품·환경·동작을 설명하는 자산을 먼저 정한다. 자산 수와 스타일은 사업과 자료에 맞추며 특정 개수·팔레트·브랜드·슬라이드 번호를 규칙으로 만들지 않는다. 한 제품의 외형과 화면 용어는 일관되게 유지한다.

이미지는 부분 자산으로 사용한다. 제목·본문·수치·산식·비교표·단위·캡션·출처는 PowerPoint에서 편집 가능하게 남긴다. 전체 슬라이드를 한 장의 생성 이미지로 대체하지 않는다. 아이콘은 의미를 돕는 보조 자산이며 중요한 정량 차트를 대신하지 않는다.

생성한 이미지를 직접 읽고 사용할 주장과 다시 대조한다. 예상과 다른 동작이 보이면 사용 위치를 바꾸거나 수정한다. 없는 성과·점수·고객·팀 인물·연동 상태를 추가하지 않는다. 시연 화면의 수량·시각·요일 표시를 실제 사용 로그로 해석하지 않는다.

자산 대장에는 `caption`, `source`, `rights`, `alt`, 근거 ID, 원본 위치·해시, 사용 장표와 crop 정보를 남긴다. 원본 사용권과 외부 공개 재배포 허용은 적용 범위를 구별한다. 원본 팀 문서나 개인정보를 외부 생성 서비스에 업로드할 수 있다고 추정하지 않는다.

다음은 용도별 캡션 예시다. 실제 상태에 맞춰 정확하게 쓴다.

- 제품 설계: **AI 생성 제품 설계안 · 화면 내용 예시 · 구현 미확인**
- 생활 장면: **AI 생성 상황 이미지 · 실제 고객 아님**
- 시연 수치: **화면 예시값 · 실제 사용 로그 아님**

캡션은 이미지 밖의 읽히는 native 글자로 표시한다. 이미지 프레임, 캡션, 출처/footer의 공간을 따로 예약하고 합계가 본문 영역을 넘지 않게 한다. 핵심 버튼·결과·단위를 잘라 없애지 않고 원본 비율을 유지한다. 세로 UI가 작아지면 작동부를 확대하고 native 설명을 대응시킨다. 아이콘 atlas는 실제 사용 크기로 각 crop의 가장자리와 옆 타일 조각을 확인한다.

## 4. 의미를 보존하는 구성으로 구현한다

비교는 같은 조건의 열·행, 제품은 실제 동작부, 시장은 범위와 계산 입력, 검증은 분모와 관찰 기간, 일정은 단계와 진행 기준을 드러낸다. 같은 카드를 색만 바꾸어 반복하지 않는다. 연속 장표의 구성 변화는 논증의 변화를 돕도록 정한다. 자료 없는 항목을 꾸민 곡선·임의 면적·가짜 인물 사진으로 채우지 않는다.

기본 레이아웃으로 충분히 표현하기 어려우면 프로젝트별 custom composition을 작성할 수 있다. 다음 조건을 모두 지킨다.

1. 모든 표시 문구와 숫자는 **현재 deck의 blocks/items에서 명시적으로 바인딩**한다. 문구를 줄여야 하면 정본 원고에서 수정 후보를 검토·병합한 뒤 출력한다. 고정 demo의 문구·숫자·slide ID 분기를 다른 팀에 복사하지 않는다.
2. 실제 그린 블록만 렌더 coverage에 기록한다. 블록 전체를 일괄 완료 처리하여 누락된 논거를 감추지 않는다. 변환 도식의 각 문구·값과 원본 block/item의 대응을 남긴다.
3. 이미지·crop·아이콘을 포함한 모든 사용 자산을 추적한다. 파일 경로나 설명용 자산을 검증되지 않는 metadata에 숨겨 출처·권리 검사를 우회하지 않는다.
4. native table/chart가 필요한 블록은 native 객체를 유지한다. 텍스트 측정·canvas 경계·font 검사도 custom composition에서 우회하지 않는다.
5. 기존 `visual_refs`, `visual_brief`, 근거와 한계를 유지한다. 구현 후 실제 렌더에서 출력·누락·위계가 원고와 맞는지 확인한다.

## 5. 대표 관계를 먼저 실제 PPTX로 확인한다

전체 제작 전에 문제의 현장/관찰 근거, 동일 조건 대안 비교, 제품 핵심 작동부, 고객 반응의 측정 조건, 초기 진입 흐름을 대표하는 장표를 선정한다. 시장·일정 등 별도의 복잡한 관계가 있으면 추가한다. 앞의 몇 장이나 고정 장표 ID를 선택하는 절차가 아니다.

대표 장표를 실제 PPTX로 렌더해 제목→주요 증거→보조 설명의 순서, UI 작동부, 값·단위·가정, caption/footer 간격, 연속 구성 차이를 직접 확인한다. 사용자가 이미 구성 방향을 정했다면 이를 적용해 진행하며 같은 승인을 다시 요청하지 않는다. 대표 장표 pass는 제작 방향 확인이며 양 덱 전체 pass가 아니다.

## 6. 양 덱 전체를 직접 읽고 수정한다

현재 사용 가능한 PowerPoint·LibreOffice·artifact-tool 중 실제 사용한 방법으로 PPTX를 렌더한다. 도구 정책을 따르고 HTML storyboard나 구조검사 성공을 실제 화면 검수로 기록하지 않는다. 최초 검수에서는 master와 pitch의 모든 장표를 직접 본다.

여덟 checks는 글자 잘림/겹침, 폰트 대체, 대비, 차트 라벨/값/단위, 이미지 crop/캡션, 정보 위계, 근거 가독성, 연속 구성 변화다. 각 장표에서 무엇이 먼저 읽히고 어떤 수치·제품 작동부·조건을 읽었는지 `visual_observations`에 쓰고, 연속 관계는 `composition_review`에 기록한다. 판단을 임의 점수나 렌더 성공 여부로 대신하지 않는다.

결함에는 장표 ID·위치·영향·수정안을 남긴다. 중요한 캡션·근거가 가려지거나 핵심 비교가 읽히지 않으면 pass로 기록하지 않는다. 실제 한글 표시와 report의 selected/substituted를 함께 확인하며 폰트 선언·등록·임베딩·다른 환경의 표시를 구별한다.

수정 후에는 새 PPTX를 다시 렌더하고 **모든 현재 PNG**의 해시를 이전 직접 검수본과 대조한다. 변경 PNG는 모두 다시 직접 읽는다. 최초 전체 검수 기록이 있고 원고·근거·원문이 같으며 PNG가 바이트 단위로 동일한 페이지에만 기존 관찰을 이어받을 수 있다. 미검수 페이지나 내용·출처가 바뀐 페이지에는 이 예외를 적용하지 않는다. notes만 바뀌었어도 관련 주장·출처·대본은 재검수한다.

현재 PPTX·deck·evidence·source documents와 렌더 SHA256을 새로 기록하고 최초 검수, 변경 페이지, 동일 바이트 페이지의 근거를 남긴다. 오래된 PPTX 해시를 새 파일에 재사용하지 않는다. 양 덱 receipt의 정확한 필드는 [계약](contracts.md)을 따른다.

## 7. 디자인과 사업근거의 판정을 분리한다

구조 검사는 패키지와 참조를, 시각 검수는 화면 품질을, 피칭 검수는 전달 흐름과 시간을 확인한다. 투자자 의미 검수는 사실과 사업 논거의 충족 여부를 판단한다. 어느 하나의 pass가 나머지를 자동 통과시키지 않는다.

실제 고객·제품·매출·팀 근거가 부족하면 그 공백을 보존한 초안으로 전달한다. 이미지의 완성도나 검증 계획을 이유로 미해결 P0/P1을 닫지 않는다. 발표 시간을 계산했으면 추정으로, 실제 리허설을 했으면 측정으로 기록한다. [실행 절차](orchestration.md)에 따라 현재 검수와 final 결과를 확인해 게시 상태를 정한다.
