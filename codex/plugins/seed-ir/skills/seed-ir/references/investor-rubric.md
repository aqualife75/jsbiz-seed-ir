# 투자자 검수 기준

이 검수는 투자를 권유하거나 투자 유치 성공을 보장하는 판정이 아니다. Seed 투자자가 내용을 이해하고 후속 검토할 수 있도록 주장·증거·사업 논리의 결함을 찾는다. 교안에서 도출한 목차별 질문은 [정석biz 노하우 기준](kdb-curriculum.json)을 따른다.

## 질문과 필수 자료부터 검토한다

사용자 지정 순서는 표지 → 문제 배경 및 최근 트렌드 → 문제 정의 → 기존 대체재의 문제점 → 해결방안 → 제품 및 서비스 소개 → 초기 고객 반응 → 수익 모델 → 시장 규모 → 초기 시장 진입 전략 → 성장 전략 → 마일스톤 → 팀 구성 → 비전이다. 문제 정의·기존 대안·제품 소개·초기 시장 진입은 각각 독립 장표 2개 이상, 나머지는 1개 이상으로 master와 pitch 각각 최소 18장을 만든다. 초기 고객 확보와 이후 성장을 분리하며 기존 대안 2장은 문제 정의 뒤·해결방안 앞에 둔다. 이번 교육 범위에서는 투자 요청·조달·금액·사용 계획을 덱·대본·질문에 넣지 않는다. 마일스톤은 목표·일정·산출물·검증 기준으로 구성한다.

v1.2의 `deck/section-briefs.json`은 사용자 지정 14목차·18개 투자자 질문의 답변과 논거를 보존한다. 각 질문의 answer, argument, 필수 항목 coverage와 출처가 서로 맞는지 직접 대조한다. 첫 질문은 해당 목차의 required_data를 담당하며 나머지 질문에도 답과 논거가 있어야 한다. 근거 ID의 존재나 문장 분량만으로 answered를 인정하지 않는다.

master 상세본에는 필요한 설명을 충분히 보존한다. `visual_refs`로 연결한 블록이 실제 질문에 답하는지 확인한다. pitch 압축본의 `source_slide_ids`를 따라 같은 `section_ids`의 master 근거가 유지되는지 확인한다. 핵심 가정·단위·한계를 압축 중 삭제하지 않는다.

필수 자료가 missing 또는 partial이면 초안은 만들 수 있지만 final은 차단된다. 없는 내부 성과나 고객 수을 만들어 채우라고 지시하지 않는다. 구체적인 자료 요청과 확인 책임자를 남긴다. 과거 회사의 성과·프로토타입 화면 수치·산업 통계가 현재 팀의 실적을 증명하는지 구분한다.

## 판정 순서

1. 먼저 원본과 근거를 대조한다. 출처가 존재하는 것과 주장을 지지하는 것은 다르다. 출처 ID·URL·해시는 형식 검사이고, 실제 의미의 일치는 검수자가 판단한다.
2. 고객의 문제, 해결책, 제품, 검증된 편익이 하나의 흐름인지 확인한다.
3. 실제 고객 반응과 지불 근거, 초기 수익모델, 시장 계산을 연결해 본다.
4. 경쟁과 고객 확보 전략, 팀의 실행 역량, 일정과 검증 마일스톤을 검토한다.
5. 장표별 메시지와 시각자료, 5분 발표에서 꼭 필요한 내용인지 판단한다.

## 목차별 확인 질문

| 목차 | 확인 질문 |
|---|---|
| 표지 | 누구의 어떤 문제를 어떻게 해결하는가 |
| 문제 배경 및 최근 트렌드 | 지금 어떤 시장 변화와 기회가 있는가 |
| 문제 정의 | 해결할 필요가 큰 문제인가 |
| 기존 대체재의 문제점 | 고객의 기존 해결 방식은 무엇인가 · 대체재가 해결하지 못하는 부분은 무엇인가 · 대안 사이의 차이와 고객이 중요하게 보는 비교 기준은 무엇인가 |
| 해결방안 | 고객 문제를 대안보다 어떻게 더 잘 해결하는가 |
| 제품 및 서비스 소개 | 가치제안이 핵심 기능으로 구현되어 있는가 · 고객이 쉽게 이해하고 사용할 수 있는가 |
| 초기 고객 반응 | 고객이 실제로 필요로 한다는 증거가 있는가 |
| 수익 모델 | 누가 어떤 방식으로 얼마를 지불하는가 |
| 시장 규모 | 당장 공략할 시장은 얼마인가 · 전체 확장 가능한 시장은 얼마인가 |
| 초기 시장 진입 전략 | 아직 알려지지 않은 팀이 첫 고객을 어떻게 얻는가 |
| 성장 전략 | 초기 검증 이후 어떻게 반복 가능한 성장을 만들 것인가 |
| 마일스톤 | 사업 목표·일정과 단계별 검증 기준은 구체적이고 현실적인가 |
| 팀 구성 | 이 팀이 제시한 사업 계획을 실현할 수 있는가 |
| 비전 | 이 사업이 궁극적으로 지향하는 목표는 무엇인가 |

사업 단계에 없는 지표를 만들어 요구하지 않는다. 매출이 없는 팀은 MVP·인터뷰를 정확하게 설명하면 된다. 확보하지 못한 증거는 후속 검증 계획으로 남긴다. 가격·고객 수·효능을 뒷받침하는 숫자가 없는데 정량화를 위해 값을 만들지 않는다.

## 중요도와 수정 지시

- `P0`: 허위·왜곡된 내부 실적, 조작한 출처, 고객·제품에 대한 심각한 오인 등 최종 사용을 막아야 할 결함.
- `P1`: 핵심 사실의 근거 부족, 시장 계산 오류, 단위·기간 불일치, 문제–해결책 단절, 핵심 마일스톤의 불명확성 등 투자 판단을 바꿀 중요한 결함.
- `P2`: 가독성·설명·비교 기준 등 이해와 설득력을 낮추는 결함.
- `P3`: 중복 표현, 부가 설명, 선택적 개선.

결함마다 정확한 `slide_id`, 주장 또는 자산 위치, 왜 문제인지, 확인한 근거, 필요한 수정, 해결 판정 조건을 적는다. 추상적인 ‘설득력 강화’ 대신 ‘시장 10억 원의 계산에 사용한 고객 수·연간 가격·기준 연도를 기록하고 합계 수정’처럼 지시한다.

```json
{
  "deck_sha256": "실제 검수한 deck 해시",
  "briefs_sha256": "실제 검수한 section-briefs 해시",
  "evidence_sha256": "실제 검수한 evidence/evidence.json 해시",
  "source_documents_sha256": "실제 검수한 data/raw/documents.json 해시",
  "reviewer": "ir_investor",
  "question_verdicts": [],
  "rationale": "검수한 원문 범위와 핵심 판단 근거",
  "verdict": "needs_revision",
  "findings": [
    {
      "id": "F001",
      "slide_id": "S05",
      "severity": "P1",
      "status": "open",
      "issue": "중요한 결함을 구체적으로 설명",
      "evidence_checked": [],
      "requested_change": "수정할 내용과 필요한 증거",
      "resolution_criteria": "해결로 인정할 조건"
    }
  ]
}
```

수정 뒤 원문과 현재 장표를 다시 읽고 조건이 충족되었을 때만 `status: resolved`로 바꾼다. P0/P1이 남아 있으면 `verdict: pass`를 쓰지 않는다. 반박 자료를 제외하거나 ‘가정’이라는 단어만 붙여 중요 결함을 없애지 않는다. 가정의 표시 자체가 적절한 해결인지 투자 판단 영향을 검토한다.

작성자는 자신의 모든 결함을 스스로 해결 판정하지 않는다. 독립 에이전트가 지원되지 않는 환경은 순차 역할 검수였다는 사실을 `rationale`에 기록한다.

위 예제는 수정 요청 형식이며 final 통과용 완성 예제가 아니다. 최종 `question_verdicts`에는 18개 질문을 빠짐없이 `{question_id, verdict, rationale}`로 기록한다. 실제 답·논거·필수 항목을 확인하고 충족한 질문만 `verdict: pass`로 표시한다. `harness.py hash --project . deck/section-briefs.json`으로 현재 지문을 확인하고 `briefs_sha256`에 기록한다. 덱·brief·근거·추출 원문 변경 후 이전 검수 해시를 재사용하지 않는다. evidence_sha256와 source_documents_sha256도 각각 해당 파일을 hash 명령으로 계산한다. 내용을 다시 확인하지 않고 해시만 갱신하지 않는다.
